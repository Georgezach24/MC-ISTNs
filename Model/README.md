# Model — Part 2 proof-of-concept

First ML pass on top of the Part 1 simulation, testing that the dataset pipeline (MATLAB → CSV → Python → trained model → metrics) works end-to-end.

## What it does

`train_model.py` loads `Dataset/dataset.csv` (generated by `PROD/monteCarloDriver.m`) and trains two classifiers — Logistic Regression and Random Forest — to predict `ServingType` per user from the **candidate-level** features (`CandBS_*` / `CandSat_*`) rather than the winning node's own metrics. This avoids the trivial case where the label is read straight off a feature that already encodes it.

`ServingType` is a **3-class** target: `Terrestrial`, `Satellite`, or `DualConnectivity` (the user is served simultaneously by both the best BS and the satellite — `PROD/simulateScenario.m`'s threshold-gated dual-connectivity rule, see `CLAUDE.md` Standards gap #7). It used to be binary (Terrestrial vs Satellite only); the shared evaluation logic for the 3-class case (macro-F1, one-vs-rest macro-AUC, 3×3 confusion matrix, per-class ROC subplots) lives in `ml_common.py` so all three scripts below stay consistent and comparable.

This is a **sanity-check model, not the Part 2 deliverable**: the label is essentially a threshold rule on `(CandBS_SNR_dB, CandSat_SNR_dB)`, so a model given both candidate SNRs is expected to reproduce that rule almost perfectly. What this run validates is that the pipeline is correct end-to-end — it isn't yet the harder ML problem (predicting from imperfect/estimated SNR, joint/fairness-aware allocation, multi-KPI objectives, etc.) that Part 2 is ultimately meant to tackle.

`BsLoad`/`SatLoad` (replacing the pre-dual-connectivity single `NodeLoad` column) are deliberately excluded from the feature set — they're a downstream consequence of `ServingType` for every user in a scenario, not an independent predictor, so including them would be circular rather than genuinely predictive.

`simulateScenario.m` can also emit `ServingType="Outage"` (no candidate above the minimum usable SNR — see `CLAUDE.md` Standards section, gap #6). All three training scripts filter these rows out before training and print how many were excluded: predicting "which of the available link(s) is/are used" is a different question from "is there any coverage at all," and mixing them would corrupt this task. The current 200-scenario dataset has 0 outage rows, so this is currently a no-op — it exists so the scripts don't silently break (or produce a misleading class-balance/metric) the day a Monte Carlo run does produce one.

**2026-08-26 update — the class-balance quirk below is fixed.** It used to be true that `Terrestrial`-only never occurred (0 rows), because (a) the satellite sub-point jitter (±3°, ~300km) was far smaller than the ~1.6-1.75 Mm visibility footprint at a 10° elevation mask, so the satellite was essentially always overhead in every scenario, and (b) "near" users were always placed at a fixed 1km from their reference BS — comfortably inside usable-SNR range, never near the actual threshold. `monteCarloDriver.m` widened the satellite jitter to ±20° (so some scenarios genuinely have no satellite coverage at all — a real LEO isn't geostationary) and replaced the fixed 1km near-user radius with a `[0.1, 4.0]` km range spanning the actual usable-SNR boundary (~2.75km in UMa NLOS, see `hysteresisStressTest.m`). All four `ServingType` states, including `Terrestrial`, now occur with real, non-trivial frequency — see the updated table below. `CLAUDE.md` gap #7 has the full before/after discussion.

## Results (200-scenario / 1313-row dataset, `rng(42)`)

Class balance (post-Outage-filter, 1015 rows / 198 scenarios): 29.7% Terrestrial / 37.6% Satellite / 32.7% DualConnectivity. 298 `Outage` rows (no candidate above minimum usable SNR) are excluded from training, same as before.

| Model | Accuracy | F1 (macro, present classes) | ROC-AUC (macro, OvR, present classes) |
|---|---|---|---|
| Logistic Regression | 0.9676 | 0.9654 | 0.9983 |
| Random Forest | 1.0000 | 1.0000 | 1.0000 |

Train/test split is grouped by `ScenarioID` (75/25), not by row — users in the same scenario share BS/satellite geometry, so a row-level split would leak scenario context between train and test.

Full metrics: `results/metrics.json`. Plots: `results/confusion_matrix_*.png`, `results/roc_curve.png`, `results/feature_importance_RandomForest.png`.

## Second pass: `train_model_geometry_only.py` — removing the SNR shortcut

`train_model.py`'s near-perfect scores aren't a meaningful ML result: the label is essentially a threshold rule on `(CandBS_SNR_dB, CandSat_SNR_dB)`, so giving the model both candidate SNRs lets it reproduce the rule almost exactly. `train_model_geometry_only.py` drops both SNR columns **and** both `*_PathLoss_dB` columns (path loss is a near-affine proxy for SNR given the fixed per-type EIRP/noise floor in `simulateScenario.m`, so keeping it would silently reintroduce the same shortcut). What's left is only what a real system knows *before* measuring a link: geometry (`CandBS_Distance_m`, `CandSat_Elevation_deg`, `CandSat_SlantRange_m`, `CandSat_Visible`) and scenario context (`NumBS`, `NumUsers`, `ScenarioType`).

| Model | Accuracy | F1 (macro, present classes) | ROC-AUC (macro, OvR, present classes) |
|---|---|---|---|
| Logistic Regression | 0.9069 | 0.8995 | 0.9859 |
| Random Forest | 0.9393 | 0.9350 | 0.9895 |

**Before dual-connectivity**, this pass showed a clearly lower, honest accuracy than the SNR-fed version (a real gap: 87.2% vs 100% RF) — the expected result of a genuinely harder problem. **After dual-connectivity but before the 2026-08-26 generator fix**, that gap had almost closed (99.15% vs 99.72% RF): with `Terrestrial`-only having vanished from the dataset, the 3-class label was largely determined by the Monte Carlo generator's *bimodal* near/far user placement itself — every "near" user was a trivial 1km from its BS (always usable) and every "far" user was 50-150km away (always unusable), so there was never a genuinely ambiguous case for geometry to get wrong. **After the generator fix** (real `Terrestrial`-only presence + a `[0.1, 4.0]` km near-user radius that actually straddles the usable-SNR boundary), the gap has reopened to a real, honest **6.1 points** (93.9% vs 100.0% RF) — geometry alone can no longer resolve the now-common borderline placements, which is exactly the kind of case a real system doesn't know about until it actually measures the link. See `CLAUDE.md` gap #7 and the thesis's discussion chapter for the fuller before/after interpretation.

Full metrics: `results_geometry_only/metrics.json`. Plots: `results_geometry_only/confusion_matrix_*.png`, `results_geometry_only/roc_curve.png`, `results_geometry_only/feature_importance_RandomForest.png`.

## Third pass: `train_model_noisy_snr.py` — a realistic middle ground

Geometry-only is arguably *more* blind than a real deployed system: real UEs do get some signal-quality estimate for candidate cells via periodic neighbor-cell measurement reports (e.g. 3GPP TS 38.331 Event A3/A5), just not the instantaneous, exact value `train_model.py` assumes. `train_model_noisy_snr.py` sits between the two: it keeps `CandBS_SNR_dB`/`CandSat_SNR_dB` as features, but adds Gaussian noise to each before the model sees them, standing in for a slightly stale/imperfect measurement report. `CandBS_PathLoss_dB`/`CandSat_PathLoss_dB` stay excluded, same reasoning as the geometry-only pass.

**2026-08-26 recalibration**: the noise magnitude used to be a single flat figure — the **measured** run-to-run SNR standard deviation from `kpiRepeatedRuns.m`'s 500 repeated realizations of the old static 6-user topology, read from `Results/kpi_link_snr_std.csv` (Terrestrial σ = 19.6721 dB, Satellite σ = 0.0682 dB). That number never mattered while every model scored ~99%+ regardless of noise — but once the generator fix (see above) made threshold-proximity actually matter, it turned out to be a poor proxy: it mixed genuine per-link channel-fading noise with variance *across different users at different distances* in that one fixed topology, and at ~20dB it was large enough to swamp the real signal, making this "realistic middle ground" experiment score *below* geometry-only for both models — the opposite of the intended three-step ordering. It's now a **per-`ScenarioType` TR 38.901 v16.1.0 Table 7.4.1-1 NLOS shadow-fading σ** instead — UMa 6dB, UMi 7.82dB (NLOS specifically, since the borderline placement distances are dominated by NLOS per `losProbability38901`, and the dataset carries no per-row LOS flag to pick the LOS σ instead). The satellite figure (0.0682dB) is unchanged — it was never the issue, consistent with the satellite channel being deterministic given geometry.

| Model | Accuracy | F1 (macro, present classes) | ROC-AUC (macro, OvR, present classes) |
|---|---|---|---|
| Logistic Regression | 0.9474 | 0.9437 | 0.9927 |
| Random Forest | 0.9312 | 0.9264 | 0.9919 |

**Before dual-connectivity**, this pass landed cleanly *between* geometry-only and exact-SNR, as designed. **After dual-connectivity but before the 2026-08-26 fixes**, all three passes had flattened to within a point of each other (~99%), for two compounding reasons: the vanished `Terrestrial`-only class (see geometry-only section) and, independently, an oversized noise σ borrowed from an unrepresentative topology. **After both fixes**, Logistic Regression shows the intended ordering cleanly (94.7%, above geometry-only's 90.7%, below exact-SNR's 96.8%). Random Forest is closer to a three-way tie with geometry-only (93.1% vs 93.9% — a 2-sample difference out of 247 test rows, not a real reversal) rather than a clean staircase; reported as-is rather than smoothed over. ROC-AUC (0.9919) still sits comfortably above geometry-only's (0.9895) for RandomForest, so the noisy SNR is still measurably informative even where it doesn't change the hard-threshold accuracy much. See `CLAUDE.md` gap #7 for the fuller before/after history, and the thesis discussion chapter for the interpretation.

Full metrics: `results_noisy_snr/metrics.json`. Plots: `results_noisy_snr/confusion_matrix_*.png`, `results_noisy_snr/roc_curve.png`, `results_noisy_snr/feature_importance_RandomForest.png`.

## Next steps

- The three passes now span the realism spectrum in both *design* and *result* again: exact SNR (100%/96.8% RF/LR) ≫ geometry-only (93.9%/90.7%) ≈/< noisy SNR (93.1%/94.7%) — a real, if not perfectly clean, gap. The 2026-08-26 generator fix (genuine `Terrestrial`-only presence, borderline user placement) and noise-σ recalibration (TR 38.901 per-`ScenarioType` NLOS shadow-fading σ instead of a flat, unrepresentative empirical figure) are both documented above and in `CLAUDE.md` gap #7.
- Further directions: predict a handover/SN-event *before* it happens using the temporal-pass data, move past `ServingType` classification to a regression/ranking target (`Capacity_Mbps`, `EnergyPerBit_uJ`), or a joint/fairness-aware multi-user objective (`PROD/simulateScenario.m`'s `Fairness.Joint` mode, see `CLAUDE.md` gap #9, is a natural source of labels here — e.g. predicting whether a user will be offloaded).
