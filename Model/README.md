# Model — Part 2 proof-of-concept

First ML pass on top of the Part 1 simulation, testing that the dataset pipeline (MATLAB → CSV → Python → trained model → metrics) works end-to-end.

## What it does

`train_model.py` loads `Dataset/dataset.csv` (generated by `PROD/monteCarloDriver.m`) and trains two classifiers — Logistic Regression and Random Forest — to predict `ServingType` per user from the **candidate-level** features (`CandBS_*` / `CandSat_*`) rather than the winning node's own metrics. This avoids the trivial case where the label is read straight off a feature that already encodes it.

`ServingType` is a **3-class** target: `Terrestrial`, `Satellite`, or `DualConnectivity` (the user is served simultaneously by both the best BS and the satellite — `PROD/simulateScenario.m`'s threshold-gated dual-connectivity rule, see `CLAUDE.md` Standards gap #7). It used to be binary (Terrestrial vs Satellite only); the shared evaluation logic for the 3-class case (macro-F1, one-vs-rest macro-AUC, 3×3 confusion matrix, per-class ROC subplots) lives in `ml_common.py` so all three scripts below stay consistent and comparable.

This is a **sanity-check model, not the Part 2 deliverable**: the label is essentially a threshold rule on `(CandBS_SNR_dB, CandSat_SNR_dB)`, so a model given both candidate SNRs is expected to reproduce that rule almost perfectly. What this run validates is that the pipeline is correct end-to-end — it isn't yet the harder ML problem (predicting from imperfect/estimated SNR, joint/fairness-aware allocation, multi-KPI objectives, etc.) that Part 2 is ultimately meant to tackle.

`BsLoad`/`SatLoad` (replacing the pre-dual-connectivity single `NodeLoad` column) are deliberately excluded from the feature set — they're a downstream consequence of `ServingType` for every user in a scenario, not an independent predictor, so including them would be circular rather than genuinely predictive.

`simulateScenario.m` can also emit `ServingType="Outage"` (no candidate above the minimum usable SNR — see `CLAUDE.md` Standards section, gap #6). All three training scripts filter these rows out before training and print how many were excluded: predicting "which of the available link(s) is/are used" is a different question from "is there any coverage at all," and mixing them would corrupt this task. The current 200-scenario dataset has 0 outage rows, so this is currently a no-op — it exists so the scripts don't silently break (or produce a misleading class-balance/metric) the day a Monte Carlo run does produce one.

**A class-balance quirk to know about**: in the current 200-scenario dataset, `Terrestrial`-only **never occurs** (0 rows) — whenever a user is close enough to have a usable BS, the satellite (EIRP 64 dBm, 10° elevation mask) is essentially always *also* usable, so `DualConnectivity` dominates over pure `Terrestrial`. Only far users (no BS in range) end up `Satellite`-only. This is a property of the current scenario geometry/link budget, not a bug — see `CLAUDE.md` gap #7 for the full discussion. One consequence: macro-averaged metrics (F1, ROC-AUC) are computed only over classes actually *present* in a given test fold (`ml_common.py`), otherwise the permanently-absent `Terrestrial` class would drag every macro score down via its by-convention 0 precision/recall, misrepresenting a data-balance fact as model difficulty.

## Results (200-scenario / 1313-row dataset, `rng(42)`)

| Model | Accuracy | F1 (macro, present classes) | ROC-AUC (macro, OvR, present classes) |
|---|---|---|---|
| Logistic Regression | 0.9858 | 0.9840 | 0.9993 |
| Random Forest | 0.9972 | 0.9968 | 1.0000 |

Train/test split is grouped by `ScenarioID` (75/25), not by row — users in the same scenario share BS/satellite geometry, so a row-level split would leak scenario context between train and test.

Full metrics: `results/metrics.json`. Plots: `results/confusion_matrix_*.png`, `results/roc_curve.png`, `results/feature_importance_RandomForest.png`.

## Running

pip install -r requirements.txt

## Second pass: `train_model_geometry_only.py` — removing the SNR shortcut

`train_model.py`'s near-perfect scores aren't a meaningful ML result: the label is essentially a threshold rule on `(CandBS_SNR_dB, CandSat_SNR_dB)`, so giving the model both candidate SNRs lets it reproduce the rule almost exactly. `train_model_geometry_only.py` drops both SNR columns **and** both `*_PathLoss_dB` columns (path loss is a near-affine proxy for SNR given the fixed per-type EIRP/noise floor in `simulateScenario.m`, so keeping it would silently reintroduce the same shortcut). What's left is only what a real system knows *before* measuring a link: geometry (`CandBS_Distance_m`, `CandSat_Elevation_deg`, `CandSat_SlantRange_m`, `CandSat_Visible`) and scenario context (`NumBS`, `NumUsers`, `ScenarioType`).

| Model | Accuracy | F1 (macro, present classes) | ROC-AUC (macro, OvR, present classes) |
|---|---|---|---|
| Logistic Regression | 0.9830 | 0.9808 | 0.9859 |
| Random Forest | 0.9915 | 0.9905 | 0.9902 |

**Before dual-connectivity**, this pass showed a clearly lower, honest accuracy than the SNR-fed version (a real gap: 87.2% vs 100% RF) — the expected result of a genuinely harder problem. **After dual-connectivity**, that gap has almost closed (99.15% vs 99.72% RF): with `Terrestrial`-only having vanished from the dataset (see the class-balance quirk above), the 3-class label is now largely determined by the Monte Carlo generator's bimodal near/far user placement itself — a user placed "near" a BS is (with this scenario's link budget) essentially always in `DualConnectivity`, and a user placed "far" is essentially always `Satellite`-only, so geometry alone gets most of the way there even without ever measuring a link's SNR. This is a real, reportable finding about *this* deployment's geometry (a regional BS cluster fully within one LEO satellite's coverage footprint at the 10° elevation mask), not a flaw in the experiment design — see `CLAUDE.md` gap #7 and the thesis's discussion chapter for the fuller interpretation.

Full metrics: `results_geometry_only/metrics.json`. Plots: `results_geometry_only/confusion_matrix_*.png`, `results_geometry_only/roc_curve.png`, `results_geometry_only/feature_importance_RandomForest.png`.

## Third pass: `train_model_noisy_snr.py` — a realistic middle ground

Geometry-only is arguably *more* blind than a real deployed system: real UEs do get some signal-quality estimate for candidate cells via periodic neighbor-cell measurement reports (e.g. 3GPP TS 38.331 Event A3/A5), just not the instantaneous, exact value `train_model.py` assumes. `train_model_noisy_snr.py` sits between the two: it keeps `CandBS_SNR_dB`/`CandSat_SNR_dB` as features, but adds Gaussian noise to each before the model sees them, standing in for a slightly stale/imperfect measurement report. `CandBS_PathLoss_dB`/`CandSat_PathLoss_dB` stay excluded, same reasoning as the geometry-only pass.

The noise magnitude isn't invented: it's the **actual measured** run-to-run SNR standard deviation from `kpiRepeatedRuns.m`'s 500 repeated realizations of the same static topology, read from `Results/kpi_link_snr_std.csv` — Terrestrial σ = 19.6721 dB, Satellite σ = 0.0682 dB. This file (not `Results/kpi_summary_by_type.csv`, used before dual-connectivity) measures the std of the *candidate* SNR directly (over usable candidates), independent of who wins — after dual-connectivity, the static 6-user topology no longer produces any `Terrestrial`-only winning row to read a "winner SNR std" from at all (same underlying cause as the class-balance quirk above). The satellite figure is small because this simulation's satellite channel is deterministic given geometry (no fading model on that side — see `CLAUDE.md` Standards section); it's used as-is rather than inflated, since a larger number wouldn't be grounded in anything the project actually models.

| Model | Accuracy | F1 (macro, present classes) | ROC-AUC (macro, OvR, present classes) |
|---|---|---|---|
| Logistic Regression | 0.9858 | 0.9840 | 0.9973 |
| Random Forest | 0.9915 | 0.9905 | 0.9965 |

**Before dual-connectivity**, this pass landed cleanly *between* geometry-only and exact-SNR, as designed. **After dual-connectivity**, all three passes are close together (Random Forest: 99.15% here, numerically tied with geometry-only's 99.15%, both just under exact-SNR's 99.72%) — the same flattened-realism-gradient effect described in the geometry-only section above. The noisy SNR still buys a *little*: its ROC-AUC (0.9965) sits above geometry-only's (0.9902), so degraded-but-present SNR information still ranks predictions slightly better even where it no longer changes the hard 0.5-threshold classification much. The clean three-step staircase this experiment was designed to show is a **before-dual-connectivity result**; see `CLAUDE.md` gap #7 for why, and the thesis discussion chapter for how the narrative changed.

Full metrics: `results_noisy_snr/metrics.json`. Plots: `results_noisy_snr/confusion_matrix_*.png`, `results_noisy_snr/roc_curve.png`, `results_noisy_snr/feature_importance_RandomForest.png`.

## Next steps

- Three passes still span the realism spectrum in *design* (exact SNR → noisy SNR → geometry-only), but after dual-connectivity was added to the simulation (`CLAUDE.md` gap #7) they no longer show a clean accuracy staircase — see the "flattened-realism-gradient" discussion in the two sections above. The connectivity-state label is now largely predictable from user placement geometry alone under this scenario's parameters, which is itself the more interesting finding going forward.
- Further directions: predict a handover/SN-event *before* it happens using the temporal-pass data, move past `ServingType` classification to a regression/ranking target (`Capacity_Mbps`, `EnergyPerBit_uJ`), a joint/fairness-aware multi-user objective, or a harder scenario-generation regime that produces genuine `Terrestrial`-only cases (e.g. a satellite elevation mask/geometry that doesn't blanket-cover the near-BS cluster) so the 3-class problem isn't dominated by user-placement geometry alone.
